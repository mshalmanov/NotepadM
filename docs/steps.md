Пошаговая история изменений проекта, внесённых в ходе работы с ассистентом.
Формат каждой записи: **Задача** → полное описание → дата. Добавляйте новые
записи в конец файла по мере выполнения работы, чтобы можно было отследить
историю решений отдельно от git-лога.

### 1. Первичный код-ревью проекта

**Описание:** Проведён полный анализ структуры проекта NotepadM (JavaFX-редактор
на Maven). Выявлены: мёртвый код от старой Swing-версии (`src/MainForm.java`,
`src/main/java/MainForm.java`, `src/META-INF/MANIFEST.MF`), опечатка в имени
поля контроллера (`pastMenuItem` вместо `pasteMenuItem`), девять `ImageView` в
`MainForm.fxml` с одинаковым `fx:id="openIcon"`, рассинхронизация версии Java
между `pom.xml` (11), `launch4j` (17) и CI (17), закоммиченный `NotepadM.iml`
при наличии правила в `.gitignore`. Предложен приоритизированный план
исправлений.

### 3. Исправление рассинхронизации FXML ↔ контроллер

**Описание:** В `MainFormController.java` поле `pastMenuItem` переименовано в
`pasteMenuItem` в соответствии с `fx:id` в `MainForm.fxml` — иначе
`@FXML`-инъекция для этого поля не срабатывала бы. В `MainForm.fxml` девяти
разным `ImageView` в тулбаре присвоены уникальные `fx:id` (`newIcon`,
`saveIcon`, `cutIcon`, `copyIcon`, `pasteIcon`, `boldIcon`, `italicsIcon`,
`underlineIcon`) вместо одинакового `openIcon` — дубликаты были валидны только
потому, что поля не объявлены в контроллере, и привели бы к `LoadException`
при первом обращении к ним. Зафиксировано коммитом `dcb9ba2` ("fix: устранены
рассинхронизации между FXML и контроллером").

**Дата:** 2026-08-27

### 10. Подсветка синтаксиса Java через RichTextFX

**Описание:** По запросу подобрана и подключена библиотека **RichTextFX**
0.11.7 для подсветки кода "как в популярных IDE" (лицензия BSD-2-Clause,
совместима с GPLv2+ проекта; альтернативы — WebView+Monaco/CodeMirror
(overkill для масштаба проекта) и ручная regex-подсветка поверх `TextArea`
(физически невозможна — `TextArea` не поддерживает стилизацию текста) — были
рассмотрены и отклонены). Реализация ограничена только Java (по решению
пользователя — автоматическое определение языка по расширению файла пока не
на чём строить, Open ещё не реализован).

Изменения: `pom.xml` — добавлена зависимость `org.fxmisc.richtext:richtextfx:0.11.7`
(транзитивно тянет `flowless`, `reactfx`, `undofx`, `wellbehavedfx`); новый
класс `ru.filive.JavaSyntaxHighlighter` — вычисление `StyleSpans` по regex
(keywords/строки/комментарии/скобки/`;`), адаптация официального демо-примера
RichTextFX; новый файл `src/main/resources/css/java-keywords.css` — цвета
подсветки и моноширинный шрифт; `MainFormController.java` — редактор вкладки
заменён с `javafx.scene.control.TextArea` на `org.fxmisc.richtext.CodeArea`
(обёрнут в `VirtualizedScrollPane` для виртуализированной прокрутки, номера
строк через `LineNumberFactory`, дебounce-подписка 500 мс на изменения текста
для пересчёта подсветки); `getCurrentTextArea()` переименован в
`getCurrentCodeArea()` и переведён на `tab.getUserData()` вместо
`tab.getContent() instanceof TextArea` (обёртка в `VirtualizedScrollPane`
сделала старую проверку нерабочей); `onCopyAction` адаптирован под новый тип
без изменения логики; `MainForm.java` — регистрация стиля на `Scene`.
Open/Save/Cut/Paste/Exit сознательно не трогались — вне рамок задачи.

Сборка (`mvn clean install`) прошла успешно, `NotepadM.exe` и jar собраны без
ошибок. Прямой запуск jar подтвердил отсутствие исключений и стабильную
работу процесса (окно открыто, не падает). Пользователь визуально подтвердил
результат скриншотом — подсветка (ключевые слова синим жирным, строки
зелёным, комментарии серым курсивом, скобки/`;` тёмным жирным) и номера строк
отображаются корректно на реальном примере Java-кода.

Документация обновлена: `docs/todo.md` (таблица функционала, пункт 18
техдолга закрыт частично, добавлены пункты 23–24 про привязку к Java и
неотписываемую подписку), `docs/architecture.md` (раздел 2 — новая

### 11. Open / Save / Exit / Cut / Paste, подтверждение несохранённых изменений

**Описание:** Реализован весь блок "Критично — базовая функциональность
блокнота" из `docs/todo.md` (пункты 1–5) плюс пункт 7 ("Важно") и несколько
доработок по ходу ручного тестирования пользователем. Работа велась
итеративно, начиная с плана, согласованного через `EnterPlanMode`.

**Изменения в `MainFormController.java`:**
- Введена модель вкладки `TabContent` (`CodeArea` + `File file` + `boolean
  dirty`) вместо голого `CodeArea` в `tab.getUserData()` — подробности в
  `docs/architecture.md`, раздел 7.
- Общий приватный метод `createTab(title, content, file)` — вынесена
  дублировавшаяся логика создания `CodeArea` (номера строк, debounce-подписка
  на подсветку), используется и `onNewAction`, и `onOpenAction`.
- **Open** — `FileChooser.showOpenDialog(...)` → `Files.readString(...)` →
  `createTab(...)`; ошибка чтения — `Alert(ERROR)` вместо старой
  заглушки-алерта "Your pressed Open!".
- **Save** — если у вкладки ещё нет файла, `FileChooser.showSaveDialog(...)`
  (это же поведение Save As); иначе — запись по существующему пути без
  диалога; заголовок вкладки обновляется на имя файла; ошибка записи —
  `Alert(ERROR)`.
- **Exit** — `Platform.exit()` вместо `System.out.println`.
- **Cut/Paste** — `CodeArea.cut()`/`CodeArea.paste()` вместо пустых заглушек.
- **Отслеживание несохранённых изменений и подтверждение закрытия** (по
  просьбе пользователя, дополнительно к исходному плану): `TabContent.dirty`
  выставляется в `true` подпиской `codeArea.plainTextChanges()`,
  зарегистрированной после начальной загрузки текста (чтобы Open/New не
  считались правкой). Общий метод `confirmClose(Tab)` показывает диалог
  Save/Don't Save/Cancel (`askSaveChanges(...)`) только если вкладка
  `dirty`, и используется в трёх местах: `Tab.setOnCloseRequest` (крестик на
  вкладке), `onExitAction`/публичный `canClose()` (перебирает все вкладки),
  и — через `canClose()` — `primaryStage.setOnCloseRequest` в
  `MainForm.java` (системный крестик окна, изначально этот путь был упущен,
  добавлен по отдельному запросу пользователя). Отмена (`Cancel`) на любом
  шаге прерывает весь процесс закрытия без побочных эффектов.
- Диалог Save/Don't Save/Cancel: кнопки получили явный `ButtonBar.ButtonData`
  (`YES`/`NO`/`CANCEL_CLOSE`) — без этого JavaFX `ButtonBar` относит кнопки
  без типа к группе `OTHER` и расставляет их с большим отступом от `Cancel`
  (реальный визуальный баг, замечен и исправлен по запросу пользователя).
  Текст диалога переработан на заголовок + пояснение (`setHeaderText`/
  `setContentText`) вместо одной длинной строки.
- Диалоги Open/Save получили `FileChooser.ExtensionFilter`
  (`*.txt`/`*.java`/`*.*`) через общий `addTextFileExtensionFilters(...)` —
  расширение файла видно в диалоге и подставляется по умолчанию при
  сохранении без явного ввода расширения.
- Публичный метод `newTab()` — используется `onNewAction` и точкой входа
  `MainForm.start()`.

**Изменения в `MainForm.java`:**
- Контроллер получается через `loader.getController()`.
- После `primaryStage.show()` вызывается `controller.newTab()` — если при
  старте не открывается никакой файл (открытие файла по аргументам
  командной строки не реализовано и не запрашивалось), приложение всегда
  начинает работу с одной пустой вкладкой, а не с пустого `TabPane`.
- `primaryStage.setOnCloseRequest(...)` вызывает `controller.canClose()` и
  отменяет закрытие окна (`event.consume()`), если пользователь нажал
  Cancel — раньше системный крестик окна закрывал приложение в обход любой
  проверки.

**Изменения в `MainForm.fxml`:** опечатка `newMenuItem` `text="Open"` →
`"New"` (правка была применена параллельно, вне сессии — на момент проверки
файл уже содержал исправленный текст).

Сборка (`mvn clean install`) проверялась после каждого значимого изменения,
`NotepadM.exe`/jar собирались без ошибок; прямой запуск jar подтверждал
отсутствие исключений при старте. Пользователь протестировал вручную весь
цикл (New/Open/Save/Cut/Paste, закрытие вкладки крестиком, File → Exit,
системный крестик окна, автосоздание пустой вкладки при старте, фильтры
расширений, вид диалога подтверждения) и подтвердил результат.

Документация обновлена: `docs/todo.md` (блок "Критично" закрыт целиком,
таблица функционала, пункт 7 закрыт, пункт 24 техдолга уточнён — утечка
подписки стала реальной, а не гипотетической, теперь когда вкладки
закрываются), `docs/architecture.md` (раздел 7 — модель `TabContent` вместо
голого `CodeArea` в `tab.getUserData()`; раздел 7.1 — уточнение про
подписку и закрытие вкладок).

**Дата:** 2026-08-28
