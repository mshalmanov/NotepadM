Журнал разработки и одновременно учебник. Каждая запись фиксирует, **что** было сделано,
**как** это работает и **почему** выбрано именно такое решение — с объяснением конструкций

## Запись 1 — 2026-07-10. Старт: каркас проекта на Rust + Slint

### Что сделано

- Создана ветка `rust` — переписывание NotepadM с Java (Swing/JavaFX) на Rust.
- Создан Cargo-проект: `Cargo.toml`, `build.rs`, `src/main.rs`, `ui/main.slint`.
- Реализован первый рабочий функционал: окно с меню, текстовый редактор,
  **Новый / Открыть / Сохранить / Выход** — то, что в JavaFX-версии оставалось заглушками.

### Технологии и зачем они

| Технология | Роль | Аналог в Java-версии |
|---|---|---|
| **Cargo** | Сборка, зависимости, запуск | Maven (`pom.xml`) |
| **Slint** | GUI-фреймворк: декларативная разметка `.slint` | JavaFX + FXML |
| **rfd** | Нативные диалоги «Открыть/Сохранить файл» | `FileChooser` |

Slint выбран потому, что его подход максимально близок к привычному JavaFX:
интерфейс описывается в отдельном файле разметки (`ui/main.slint` ≈ `MainForm.fxml`),
а логика живёт в коде (`src/main.rs` ≈ `MainFormController.java`). При этом один и тот же
код собирается под Windows, Linux и macOS без изменений — кроссплатформенность бесплатно.

### Как устроен проект

```
Cargo.toml      — манифест: имя пакета, зависимости (аналог pom.xml)
build.rs        — скрипт сборки: компилирует ui/main.slint в Rust-код
ui/main.slint   — разметка окна: меню, текстовое поле, свойства, callbacks
src/main.rs     — точка входа: создаёт окно, подключает обработчики меню
```

Ключевое отличие от JavaFX: FXML загружается и разбирается **при запуске** программы
(ошибка в разметке = падение у пользователя), а `.slint` компилируется в Rust-код
**при сборке** — опечатка в разметке просто не даст собрать программу. Это общий принцип
Rust: ловить ошибки как можно раньше, на этапе компиляции.

### Конструкции Rust, встретившиеся в этой записи

**1. `slint::include_modules!()`** — макрос. Вставляет в программу код, который `build.rs`
сгенерировал из `main.slint` (структуру `MainWindow` с методами). Макросы с `!` — это
генерация кода на этапе компиляции; в Java ближайший аналог — annotation processing.

**2. Замыкания (closures) вместо анонимных классов.** В Java обработчик — это
`new ActionListener() { ... }` или метод с аннотацией `@FXML`. В Rust — замыкание:

```rust
ui.on_new_file(move || {
    // тело обработчика
});
```

`move` означает «замыкание забирает используемые переменные во владение».

**3. Владение (ownership) — центральная идея Rust.** У каждого значения ровно один
владелец; когда владелец выходит из области видимости, память освобождается. Нет ни
сборщика мусора (как в Java), ни ручного `free` (как в C). Компилятор проверяет это
статически — отсюда большинство «странных» конструкций ниже.

**4. `Rc<RefCell<Option<PathBuf>>>`** — путь к текущему файлу, разложим по слоям:

- `PathBuf` — путь к файлу (владеющий, кроссплатформенный: сам знает про `\` и `/`).
- `Option<...>` — «значение может отсутствовать». Замена `null`: в Rust нет NPE,
  компилятор заставляет обработать случай «файла ещё нет» явно.
- `RefCell<...>` — разрешает изменять значение через общую ссылку, проверяя
  корректность в рантайме (`borrow()` / `borrow_mut()`).
- `Rc<...>` — счётчик ссылок: несколько владельцев одного значения.

Зачем всё это: обработчики «Открыть» и «Сохранить» — разные замыкания, и обоим нужен
доступ к одному изменяемому пути. В Java это было бы просто поле класса; в Rust
совместное изменяемое состояние оформляется явно: `Rc` даёт совместное владение,
`RefCell` — контролируемую изменяемость.

**5. `ui.as_weak()` / `ui.unwrap()`** — слабая ссылка на окно. Если замыкание захватит
окно «сильно», получится цикл ссылок (окно владеет обработчиком, обработчик — окном),
и память не освободится. Знакомая проблема из Java (утечки слушателей) — но здесь она
решается явным типом, а не осторожностью программиста.

**6. `Result` и `match` вместо исключений.** В Rust нет `try/catch`. Функция, которая
может не сработать, возвращает `Result<T, E>` — либо `Ok(значение)`, либо `Err(ошибка)`:

```rust
match fs::read_to_string(&path) {
    Ok(text) => { /* показать текст */ }
    Err(err) => { /* показать диалог с ошибкой */ }
}
```

Компилятор не даст молча проигнорировать ошибку — она часть сигнатуры функции.

**7. Сигнатура `main`**: `fn main() -> Result<(), slint::PlatformError>` — даже точка
входа честно объявляет, что может завершиться ошибкой (например, нет графической среды).

### Как собрать и запустить

```
cargo run            # отладочная сборка + запуск
cargo build --release   # оптимизированная сборка → target/release/notepadm.exe
cargo check          # быстрая проверка кода без сборки
cargo clippy         # линтер: советы по идиоматичному Rust
cargo fmt            # автоформатирование кода
```

Первая сборка долгая (компилируются все зависимости, включая Slint), дальше — быстро:
пересобирается только изменённое.

## Запись 2 — 2026-07-10. Очистка ветки от Java-наследия

### Что сделано

С ветки `rust` удалены все файлы исходного Java-проекта:

- `pom.xml`, `NotepadM.iml` — манифест Maven и файл проекта IntelliJ IDEA
- `src/main/java/`, `src/MainForm.java`, `src/META-INF/` — исходники Swing-версии
  (включая дубликат `MainForm.java`, лежавший вне Maven-структуры)
- `src/main/resources/images/` — иконки тулбара и `NotepadM.ICO`
- `.github/workflows/main.yml` — CI-конвейер Maven + Launch4j (на Rust-ветке он бы
  просто падал; для Rust позже напишем свой, с матрицей Windows/Linux/macOS)

`.gitignore` переписан под Rust: осталось только `/target/` (папка сборки Cargo),
`.idea` и `/backup/`.

### Почему это безопасно

Git хранит полную историю: все удалённые файлы остаются в ветках `master` (Swing)
и `dev` (JavaFX) и в прошлых коммитах. Удаление на одной ветке ничего не уничтожает —
в любой момент файл можно вернуть командой `git checkout master -- путь/к/файлу`.
Это важная привычка при работе с git: не держать «мёртвый» код на ветке «на всякий
случай» — история и есть этот «всякий случай».

### Урок про структуру

В Java-проекте структура папок диктуется инструментом (`src/main/java`,
`src/main/resources` — соглашение Maven). В Rust соглашение проще и его контролирует
Cargo: `src/main.rs` — точка входа, `build.rs` — скрипт сборки, всё остальное —
на усмотрение проекта (наша папка `ui/` для разметки — собственное решение,
Cargo про неё узнаёт из `build.rs`).

## Запись 3 — 2026-07-10. Вкладки и признак несохранённых изменений

### Что сделано

- Несколько документов во вкладках — паритет с JavaFX-версией (`TabPane` из ветки `dev`)
  и сразу больше: у вкладок есть кнопка закрытия «✕» и признак изменённости.
- «Грязные» (изменённые, но не сохранённые) документы помечаются `*` в заголовке
  вкладки и окна; при закрытии такой вкладки — диалог подтверждения.
- «Открыть» стал умнее: файл открывается в новой вкладке, но если текущая вкладка
  пустая и нетронутая — переиспользуется она (не плодим пустышки).
- После закрытия последней вкладки автоматически создаётся новая пустая —
  окно никогда не остаётся без редактора.

### Ключевая идея: источник истины — в Rust

Состояние приложения — `Vec<Document>` (структура: путь, текст, флаг dirty) — живёт
в Rust-коде. UI ничего не хранит сам: он лишь отображает модель вкладок
и текст активного документа, а о действиях пользователя сообщает через callbacks.
Это то же разделение Model/View, что в JavaFX, но граница жёстче: у разметки
физически нет доступа к `Vec<Document>`, она видит только то, что ей отдали.

### Новое в Slint

**1. Модели и `for`-повторение.** В разметке объявлено свойство-список
`in-out property <[TabInfo]> tabs`, а панель вкладок строится циклом:

```slint
for tab[i] in root.tabs: Rectangle { ... }
```

Из Rust туда передаётся `VecModel` — «живой» список: любое изменение
(`set_vec`, `set_row_data`) автоматически перестраивает интерфейс. Аналог
`ObservableList` в JavaFX, на котором строился `TabPane`.

**2. Общие структуры.** `export struct TabInfo { title, dirty }` в `.slint`-файле —
компилятор Slint генерирует одноимённую Rust-структуру, и обе стороны работают
с одним типом. В JavaFX подобное требовало бы ручного класса-модели.

**3. Порядок объявления = порядок слоёв.** Внутри вкладки сначала объявлена
`TouchArea` на всю площадь (клик = переключить вкладку), а затем содержимое с кнопкой
«✕» и её собственной `TouchArea`. Элементы, объявленные позже, лежат выше и получают
клики первыми — так «✕» перехватывает клик у вкладки. Это правило стоит запомнить:
z-порядок в Slint определяется порядком в коде.

**4. Реактивный заголовок окна.** `title` — это выражение от `tabs` и `current-tab`:
поменялась модель — пересчитался заголовок. Ничего не нужно обновлять вручную.

### Новое в Rust

**1. Своя структура с методами:**

```rust
#[derive(Default)]
struct Document {
    path: Option<PathBuf>,
    text: String,
    dirty: bool,
}
impl Document {
    fn title(&self) -> String { ... }
}
```

`struct` + отдельный блок `impl` — так в Rust устроены «классы». `#[derive(Default)]`
автоматически создаёт конструктор «все поля пустые» (`Document::default()`).
Наследования в Rust нет — вместо иерархий классов используются структуры и трейты.

**2. Цепочки методов `Option` вместо проверок на null.** Заголовок вкладки:

```rust
self.path.as_ref()                      // Option<&PathBuf>
    .and_then(|p| p.file_name())        // Option<&OsStr> — имя файла, если есть
    .map(|n| n.to_string_lossy().into_owned())      // Option<String>
    .unwrap_or_else(|| String::from("Новый файл"))  // String — запасное значение
```

В Java это была бы лестница `if (x != null)`. Здесь каждый шаг явно сохраняет
«значения может не быть», а в конце обязательно указано, что делать при отсутствии.

**3. `let ... else` — ранний выход.** Идиома «достань значение или выйди»:

```rust
let Some(path) = dialog.pick_file() else {
    return; // пользователь отменил диалог
};
// дальше path — уже просто PathBuf, без Option
```

**4. Область займа (borrow scope).** В обработчике закрытия вкладки данные читаются
во вложенном блоке `{ ... }`, чтобы заём `RefCell` закончился **до** показа модального
диалога, а `borrow_mut()` брался уже после. Правило «либо много читателей, либо один
писатель» действует и в рантайме: пересечение `borrow()` и `borrow_mut()` — паника.
Вложенный блок — стандартный способ ограничить время жизни займа.

**5. `usize` против `i32`.** Slint передаёт индексы как `int` (`i32`), Rust индексирует
только типом `usize` — отсюда явные преобразования `index as usize` / `as i32`.
Rust никогда не преобразует числа неявно, даже «безопасные» расширения.

### Как проверить

`cargo run` → создать пару вкладок («Файл → Новый»), переключаться между ними,
набрать текст (появится `*`), закрыть изменённую вкладку (спросит подтверждение),
открыть файл при пустой вкладке (займёт её) и при непустой (создаст новую).
