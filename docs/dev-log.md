## Запись 1 — 2026-07-10. Старт: каркас проекта на Rust + Slint

### Что сделано

- Создана ветка `rust` — переписывание NotepadM с Java (Swing/JavaFX) на Rust.
- Создан Cargo-проект: `Cargo.toml`, `build.rs`, `src/main.rs`, `ui/main.slint`.
- Реализован первый рабочий функционал: окно с меню, текстовый редактор,
  **Новый / Открыть / Сохранить / Выход** — то, что в JavaFX-версии оставалось заглушками.

### Технологии и зачем они

| Технология | Роль | Аналог в Java-версии |
|---|---|---|
| **Cargo** | Сборка, зависимости, запуск | Maven (`pom.xml`) |
| **Slint** | GUI-фреймворк: декларативная разметка `.slint` | JavaFX + FXML |
| **rfd** | Нативные диалоги «Открыть/Сохранить файл» | `FileChooser` |

Slint выбран потому, что его подход максимально близок к привычному JavaFX:
интерфейс описывается в отдельном файле разметки (`ui/main.slint` ≈ `MainForm.fxml`),
а логика живёт в коде (`src/main.rs` ≈ `MainFormController.java`). При этом один и тот же
код собирается под Windows, Linux и macOS без изменений — кроссплатформенность бесплатно.

### Как устроен проект

```
Cargo.toml      — манифест: имя пакета, зависимости (аналог pom.xml)
build.rs        — скрипт сборки: компилирует ui/main.slint в Rust-код
ui/main.slint   — разметка окна: меню, текстовое поле, свойства, callbacks
src/main.rs     — точка входа: создаёт окно, подключает обработчики меню
```

Ключевое отличие от JavaFX: FXML загружается и разбирается **при запуске** программы
(ошибка в разметке = падение у пользователя), а `.slint` компилируется в Rust-код
**при сборке** — опечатка в разметке просто не даст собрать программу. Это общий принцип
Rust: ловить ошибки как можно раньше, на этапе компиляции.

### Конструкции Rust, встретившиеся в этой записи

**1. `slint::include_modules!()`** — макрос. Вставляет в программу код, который `build.rs`
сгенерировал из `main.slint` (структуру `MainWindow` с методами). Макросы с `!` — это
генерация кода на этапе компиляции; в Java ближайший аналог — annotation processing.

**2. Замыкания (closures) вместо анонимных классов.** В Java обработчик — это
`new ActionListener() { ... }` или метод с аннотацией `@FXML`. В Rust — замыкание:

```rust
ui.on_new_file(move || {
    // тело обработчика
});
```

`move` означает «замыкание забирает используемые переменные во владение».

**3. Владение (ownership) — центральная идея Rust.** У каждого значения ровно один
владелец; когда владелец выходит из области видимости, память освобождается. Нет ни
сборщика мусора (как в Java), ни ручного `free` (как в C). Компилятор проверяет это
статически — отсюда большинство «странных» конструкций ниже.

**4. `Rc<RefCell<Option<PathBuf>>>`** — путь к текущему файлу, разложим по слоям:

- `PathBuf` — путь к файлу (владеющий, кроссплатформенный: сам знает про `\` и `/`).
- `Option<...>` — «значение может отсутствовать». Замена `null`: в Rust нет NPE,
  компилятор заставляет обработать случай «файла ещё нет» явно.
- `RefCell<...>` — разрешает изменять значение через общую ссылку, проверяя
  корректность в рантайме (`borrow()` / `borrow_mut()`).
- `Rc<...>` — счётчик ссылок: несколько владельцев одного значения.

Зачем всё это: обработчики «Открыть» и «Сохранить» — разные замыкания, и обоим нужен
доступ к одному изменяемому пути. В Java это было бы просто поле класса; в Rust
совместное изменяемое состояние оформляется явно: `Rc` даёт совместное владение,
`RefCell` — контролируемую изменяемость.

**5. `ui.as_weak()` / `ui.unwrap()`** — слабая ссылка на окно. Если замыкание захватит
окно «сильно», получится цикл ссылок (окно владеет обработчиком, обработчик — окном),
и память не освободится. Знакомая проблема из Java (утечки слушателей) — но здесь она
решается явным типом, а не осторожностью программиста.

**6. `Result` и `match` вместо исключений.** В Rust нет `try/catch`. Функция, которая
может не сработать, возвращает `Result<T, E>` — либо `Ok(значение)`, либо `Err(ошибка)`:

```rust
match fs::read_to_string(&path) {
    Ok(text) => { /* показать текст */ }
    Err(err) => { /* показать диалог с ошибкой */ }
}
```

Компилятор не даст молча проигнорировать ошибку — она часть сигнатуры функции.

**7. Сигнатура `main`**: `fn main() -> Result<(), slint::PlatformError>` — даже точка
входа честно объявляет, что может завершиться ошибкой (например, нет графической среды).

### Как собрать и запустить

```
cargo run            # отладочная сборка + запуск
cargo build --release   # оптимизированная сборка → target/release/notepadm.exe
cargo check          # быстрая проверка кода без сборки
cargo clippy         # линтер: советы по идиоматичному Rust
cargo fmt            # автоформатирование кода
```

Первая сборка долгая (компилируются все зависимости, включая Slint), дальше — быстро:
пересобирается только изменённое.

### Почему это безопасно

Git хранит полную историю: все удалённые файлы остаются в ветках `master` (Swing)
и `dev` (JavaFX) и в прошлых коммитах. Удаление на одной ветке ничего не уничтожает —
в любой момент файл можно вернуть командой `git checkout master -- путь/к/файлу`.
Это важная привычка при работе с git: не держать «мёртвый» код на ветке «на всякий
случай» — история и есть этот «всякий случай».

### Урок про структуру

В Java-проекте структура папок диктуется инструментом (`src/main/java`,
`src/main/resources` — соглашение Maven). В Rust соглашение проще и его контролирует
Cargo: `src/main.rs` — точка входа, `build.rs` — скрипт сборки, всё остальное —
на усмотрение проекта (наша папка `ui/` для разметки — собственное решение,
Cargo про неё узнаёт из `build.rs`).

## Запись 3 — 2026-07-10. Вкладки и признак несохранённых изменений

### Что сделано

- Несколько документов во вкладках — паритет с JavaFX-версией (`TabPane` из ветки `dev`)
  и сразу больше: у вкладок есть кнопка закрытия «✕» и признак изменённости.
- «Грязные» (изменённые, но не сохранённые) документы помечаются `*` в заголовке
  вкладки и окна; при закрытии такой вкладки — диалог подтверждения.
- «Открыть» стал умнее: файл открывается в новой вкладке, но если текущая вкладка
  пустая и нетронутая — переиспользуется она (не плодим пустышки).
- После закрытия последней вкладки автоматически создаётся новая пустая —
  окно никогда не остаётся без редактора.

### Ключевая идея: источник истины — в Rust

Состояние приложения — `Vec<Document>` (структура: путь, текст, флаг dirty) — живёт
в Rust-коде. UI ничего не хранит сам: он лишь отображает модель вкладок
и текст активного документа, а о действиях пользователя сообщает через callbacks.
Это то же разделение Model/View, что в JavaFX, но граница жёстче: у разметки
физически нет доступа к `Vec<Document>`, она видит только то, что ей отдали.

### Новое в Slint

**1. Модели и `for`-повторение.** В разметке объявлено свойство-список
`in-out property <[TabInfo]> tabs`, а панель вкладок строится циклом:

```slint
for tab[i] in root.tabs: Rectangle { ... }
```

Из Rust туда передаётся `VecModel` — «живой» список: любое изменение
(`set_vec`, `set_row_data`) автоматически перестраивает интерфейс. Аналог
`ObservableList` в JavaFX, на котором строился `TabPane`.

**2. Общие структуры.** `export struct TabInfo { title, dirty }` в `.slint`-файле —
компилятор Slint генерирует одноимённую Rust-структуру, и обе стороны работают
с одним типом. В JavaFX подобное требовало бы ручного класса-модели.

**3. Порядок объявления = порядок слоёв.** Внутри вкладки сначала объявлена
`TouchArea` на всю площадь (клик = переключить вкладку), а затем содержимое с кнопкой
«✕» и её собственной `TouchArea`. Элементы, объявленные позже, лежат выше и получают
клики первыми — так «✕» перехватывает клик у вкладки. Это правило стоит запомнить:
z-порядок в Slint определяется порядком в коде.

**4. Реактивный заголовок окна.** `title` — это выражение от `tabs` и `current-tab`:
поменялась модель — пересчитался заголовок. Ничего не нужно обновлять вручную.

### Новое в Rust

**1. Своя структура с методами:**

```rust
#[derive(Default)]
struct Document {
    path: Option<PathBuf>,
    text: String,
    dirty: bool,
}
impl Document {
    fn title(&self) -> String { ... }
}
```

`struct` + отдельный блок `impl` — так в Rust устроены «классы». `#[derive(Default)]`
автоматически создаёт конструктор «все поля пустые» (`Document::default()`).
Наследования в Rust нет — вместо иерархий классов используются структуры и трейты.

**2. Цепочки методов `Option` вместо проверок на null.** Заголовок вкладки:

```rust
self.path.as_ref()                      // Option<&PathBuf>
    .and_then(|p| p.file_name())        // Option<&OsStr> — имя файла, если есть
    .map(|n| n.to_string_lossy().into_owned())      // Option<String>
    .unwrap_or_else(|| String::from("Новый файл"))  // String — запасное значение
```

В Java это была бы лестница `if (x != null)`. Здесь каждый шаг явно сохраняет
«значения может не быть», а в конце обязательно указано, что делать при отсутствии.

**3. `let ... else` — ранний выход.** Идиома «достань значение или выйди»:

```rust
let Some(path) = dialog.pick_file() else {
    return; // пользователь отменил диалог
};
// дальше path — уже просто PathBuf, без Option
```

**4. Область займа (borrow scope).** В обработчике закрытия вкладки данные читаются
во вложенном блоке `{ ... }`, чтобы заём `RefCell` закончился **до** показа модального
диалога, а `borrow_mut()` брался уже после. Правило «либо много читателей, либо один
писатель» действует и в рантайме: пересечение `borrow()` и `borrow_mut()` — паника.
Вложенный блок — стандартный способ ограничить время жизни займа.

**5. `usize` против `i32`.** Slint передаёт индексы как `int` (`i32`), Rust индексирует
только типом `usize` — отсюда явные преобразования `index as usize` / `as i32`.
Rust никогда не преобразует числа неявно, даже «безопасные» расширения.

## Запись 4 — 2026-07-10. «Сохранить как…», «О программе», защита при выходе, CI

### Что сделано

- **«Сохранить как…»** в меню «Файл» (с разделителем перед «Выход» — `MenuSeparator`).
- **«О программе»** в меню «Справка»: название, версия, лицензия, автор.
- **Защита от потери данных при выходе**: и пункт меню «Выход», и крестик окна
  проверяют несохранённые документы и спрашивают подтверждение, перечисляя файлы.
- **CI на GitHub Actions** (`.github/workflows/ci.yml`): на каждый push в ветку `rust`
  проект собирается под **Windows, Linux и macOS** — это и есть практическая проверка
  кроссплатформенности. Плюс проверка форматирования и линтер.

### Урок: выделение общей логики вместо копипасты

«Сохранить» и «Сохранить как…» отличаются одной деталью: показывать ли диалог выбора
файла при известном пути. Вместо двух почти одинаковых обработчиков — одна функция
с параметром:

```rust
fn save_document(docs: &Rc<RefCell<Vec<Document>>>, tabs: &VecModel<TabInfo>,
                 index: usize, always_ask: bool)
```

Оба обработчика меню превратились в две строки. То же с проверкой при выходе:
`dirty_titles()` + `confirm_discard()` используются и в «Выход», и в обработчике
крестика окна.

### Новое в Rust и Slint

**1. Перехват закрытия окна.** `ui.window().on_close_requested(...)` — обработчик
обязан вернуть значение: `CloseRequestResponse::HideWindow` (закрыть) или
`KeepWindowShown` (отменить закрытие). Обратите внимание: это перечисление (`enum`) —
компилятор не даст вернуть что-то третье или забыть вернуть ответ. В JavaFX аналог —
`setOnCloseRequest` + `event.consume()`, где «отмену» легко забыть.

**2. `env!` — чтение переменных на этапе компиляции.** Версия в «О программе» берётся
из `Cargo.toml` через `env!("CARGO_PKG_VERSION")` и вшивается в бинарник как константа.
Поменяли версию в манифесте — диалог обновится сам при следующей сборке.

**3. Итераторы: `filter` + `map` + `collect`.** Список несохранённых файлов:

```rust
docs.iter()                      // итератор по документам
    .filter(|doc| doc.dirty)     // оставить только изменённые
    .map(Document::title)        // документ → его заголовок
    .collect()                   // собрать в Vec<String>
```

Аналог Stream API из Java (`stream().filter().map().collect()`), но без накладных
расходов: цепочка компилируется в обычный цикл.

**4. `cargo fmt` и `cargo clippy` — штатные инструменты качества.** `fmt` приводит
код к каноническому формату (никаких споров о стиле), `clippy` — линтер с сотнями
правил, который учит идиоматичному Rust (наш код прошёл без замечаний). Оба включены
в CI как обязательные проверки: неотформатированный код или предупреждение линтера
валят сборку.

### Как устроен CI (`.github/workflows/ci.yml`)

- `strategy.matrix.os` — один и тот же job запускается на трёх ОС параллельно;
  `fail-fast: false` — падение на одной ОС не отменяет остальные.
- `Swatinem/rust-cache` — кэширует скомпилированные зависимости между запусками
  (без него каждый CI-прогон собирал бы Slint с нуля по несколько минут).
- Только Linux требует системных пакетов (`libxkbcommon-dev`, `libfontconfig1-dev`) —
  на Windows/macOS всё нужное есть из коробки.
- Собранные бинарники выкладываются как артефакты — можно скачать
  `NotepadM-Windows/Linux/macOS` прямо со страницы прогона в GitHub.

### Как проверить

`cargo run` → набрать текст в двух вкладках, нажать «Выход» — диалог перечислит оба
файла; «Сохранить как…» предложит имя текущей вкладки; «Справка → О программе»
покажет версию 0.1.0 из Cargo.toml. CI проверится после push на GitHub.

```
git show origin/dev:src/main/resources/images/NotepadM.png > ui/images/NotepadM.png
```

`git show ветка:путь` печатает содержимое файла из любого коммита. Это тот самый
принцип из записи 2: история git — надёжнее, чем «мёртвые» файлы на ветке.

### Новое в Slint

**1. `@image-url("...")` — ресурсы времени компиляции.** Путь разрешается относительно
`.slint`-файла, а картинка **встраивается в бинарник**. Сравните с Java-версией, где
была целая история с путями: в Swing-версии дубликат кода грузил иконки с диска
(`new ImageIcon("src/images/...")` — сломалось бы после сборки в jar), рабочий вариант —
через classpath (`getClass().getResource(...)`). В Slint неверный путь = ошибка сборки,
а готовому `.exe` не нужны файлы рядом.

**2. Функции элементов.** У `TextEdit` есть встроенные функции `cut()`, `copy()`,
`paste()` — кнопки тулбара вызывают их напрямую из разметки, без похода в Rust:

```slint
Button { icon: @image-url("images/Cut.png"); clicked => { editor.cut(); } }
```

Для этого элементу дано имя: `editor := TextEdit { ... }` (синтаксис `имя :=` —
как `fx:id` в FXML). Правило разделения обязанностей сохраняется: работа с буфером
обмена — чисто UI-дело, состояние документов оно не трогает (текст меняется →
`edited` → Rust узнаёт как обычно).

**3. `icon` у `MenuItem`, `Button` и `Window`** — одно и то же свойство типа `image`
в разных ролях: пункт меню, кнопка, иконка приложения.

«вырезать» → «вставить»; Новый/Открыть/Сохранить с тулбара работают как из меню.

## Запись 7 — 2026-07-10. Поддержка HTML: фильтры и предпросмотр в браузере

### Что сделано

- **HTML в диалогах**: фильтр `*.html, *.htm` добавлен в «Открыть» и «Сохранить».
- **«Файл → Предпросмотр в браузере»**: текущий документ открывается в браузере
  по умолчанию. Схема выбора источника:
  - файл сохранён и без правок → браузеру отдаётся сам файл (работают относительные
    ссылки и картинки, лежащие рядом);
  - файл не сохранён или есть правки → текущий текст выгружается во временный файл
    `notepadm-preview.html` и открывается он.
- Новая зависимость: крейт **`open`** — кроссплатформенное «открыть в программе
  по умолчанию» (на Windows это `start`, на Linux `xdg-open`, на macOS `open` —
  крейт прячет эти различия).

### Почему именно предпросмотр в браузере

Рассматривались три уровня «поддержки HTML»:

1. **Фильтры + предпросмотр в браузере** — выбрано: быстро, надёжно, ноль новых
   сложных зависимостей, и это честный сценарий «правлю разметку — смотрю результат».
2. **Подсветка синтаксиса** — стандартный `TextEdit` в Slint работает только
   с простым текстом; подсветка означает собственный редакторский виджет с нуля.
   Отдельный большой этап, отложен (добавлен в план).
3. **Рендеринг внутри окна** — в Slint нет HTML-движка; встраивание webview
   тяжёлое и хрупкое. Отклонено.

### Новое в Rust

**1. `match` по кортежу.** Выбор «что показывать» — одно выражение по двум полям сразу:

```rust
match (&doc.path, doc.dirty) {
    (Some(path), false) => Ok(path.clone()), // сохранён и актуален
    _ => { /* текст во временный файл */ }
}
```

`_` покрывает остальные комбинации (нет пути / есть правки). Компилятор проверяет,
что разобраны все случаи.

**2. `std::env::temp_dir()`** — кроссплатформенный путь к временной папке
(`%TEMP%` на Windows, `/tmp` на Linux). Ещё одно место, где ОС-различия закрывает
стандартная библиотека, а не наш код.

**3. Цепочка `Result`: `map` и `and_then`.** Записать файл → открыть браузер —
два шага, каждый может дать ошибку:

```rust
fs::write(&tmp, ...).map(|_| tmp)                      // Result<PathBuf, Error>
target.and_then(|path| open::that(&path).map(|_| path)) // оба шага в одну цепочку
```

`map` преобразует успешное значение, `and_then` подключает следующий шаг, который
сам может вернуть ошибку. Любая ошибка «проваливается» в конец цепочки — обрабатывается
один раз, в одном месте.

### Как проверить

`cargo run` → набрать HTML (`<h1>Привет</h1>`) → «Файл → Предпросмотр в браузере» —
откроется браузер с заголовком. Сохранить как `.html`, ещё раз предпросмотр —
откроется уже сам сохранённый файл.

  Ctrl+W (закрыть вкладку), F3 (искать далее), Esc (закрыть панель поиска).
  Ctrl+C/V/X/Z встроены в сам редактор.

### Новое в Slint

**1. `FocusScope` и «всплытие» клавиш.** Нажатия обрабатывает сфокусированный
элемент (редактор, поле ввода); всё, что он не съел (например, Ctrl+N), «всплывает»
вверх по дереву до нашего `FocusScope` с обработчиком `key-pressed`. Обработчик
обязан вернуть `accept` (событие обработано) или `reject` (пропустить дальше) —
снова enum вместо легко забываемого `event.consume()` из JavaFX.

**2. Публичные функции компонента.** В разметке объявлена
`public function highlight(start: int, end: int)` — Rust вызывает её как
`ui.invoke_highlight(...)`. До сих пор общение шло только «UI → Rust» (callbacks);
это первый канал «Rust → UI» помимо свойств.

**3. Почему панель поиска не через `if`.** К элементам внутри условного блока
`if visible : ...` нельзя обращаться извне (их может не существовать) — а нам нужен
`search-input.focus()`. Поэтому панель существует всегда, но при скрытии
схлопывается в ноль по высоте (`height: visible ? auto : 0` + `clip`).

**4. Приватные функции разметки.** `function open-search(to-replace: bool)` —
общий код для меню, тулбара и хоткеев прямо в `.slint`, без похода в Rust
(фокус и видимость — чисто UI-дела).

### Новое в Rust

**1. Байтовые смещения и Юникод.** Поиск возвращает границы вхождений в **байтах**
UTF-8 (кириллическая буква — 2 байта). Наивный регистронезависимый поиск через
`to_lowercase()` обеих строк дал бы «поплывшие» смещения: у некоторых символов
при смене регистра меняется длина в байтах. Решение в `find_matches`: строим
строчную копию текста вместе с **картой соответствия байтов** оригиналу.

**2. `char_indices()`** — итератор по символам вместе с их байтовыми позициями;
единственный правильный способ ходить по строке, когда нужны смещения
(`text[i]` в Rust вообще не компилируется — намеренно).

**3. `Option::filter` и `is_some_and`.** Проверка «замена всё ещё указывает
на актуальное место» (текст могли отредактировать после поиска):

```rust
search.current.filter(|(s, e)| text.get(*s..*e).is_some_and(|sl| sl == term))
```

`text.get(a..b)` — «безопасная» индексация: возвращает `Option`, а не панику,
если границы устарели.

**4. Rust вызывает функцию разметки**: `ui.invoke_highlight(start, end)` и даже
`ui.invoke_find_next(...)` из обработчика замены — сгенерированные методы
`invoke_*` появляются для каждого callback и публичной функции компонента.

### Как проверить

`cargo run` → Ctrl+F → ввести слово → Enter/F3 листает вхождения с выделением
и счётчиком; «Учитывать регистр» снять/поставить; Ctrl+H → «Заменить» меняет
подсвеченное и прыгает к следующему, «Заменить все» — разом (в т.ч. по кириллице
в разном регистре); Ctrl+N/O/S/Shift+S/W, Esc.

Тесты живут прямо в файле с кодом, в модуле под атрибутом `#[cfg(test)]` —
в обычную сборку они не попадают:

```rust
#[cfg(test)]
mod tests {
    use super::*; // видим всё из основного файла

    #[test]
    fn finds_all_occurrences() {
        assert_eq!(find_matches("aXbXc", "X", true), vec![(1, 2), (3, 4)]);
    }
}
```

- `cargo test` — собрать и прогнать всё; `cargo test имя` — по подстроке имени.
- `assert_eq!`/`assert_ne!`/`assert!` — при провале печатают оба значения.
- Сравните с Java: не нужен ни JUnit, ни отдельная папка `src/test/java`,
  ни аннотации фреймворка — тесты встроены в язык и сборщик.
- Заметьте, какие функции легко тестировать: «чистые» (`find_matches`,
  `decode_bytes`) — вход → выход, без UI и файловой системы. Это довод
  за то, чтобы выносить логику из обработчиков в свободные функции.

### Новое в Rust: кодировки

- **`fs::read` вместо `fs::read_to_string`**: получаем `Vec<u8>` — сырые байты
  без предположений о кодировке. `String` в Rust всегда UTF-8 по определению,
  поэтому «прочитать строку в 1251» в принципе невозможно — сначала байты,
  потом явное декодирование.
- **`chardetng`** — детектор кодировок из Firefox: скормили байты → получили

  сгенерировать `#[derive(Default)]` — у ссылки нет очевидного «нуля»,
  задаём свой умолчальный вариант (UTF-8) вручную.
- **`&'static`** — ссылка со временем жизни «вся программа»: таблицы кодировок
  вшиты в библиотеку, поэтому хранить такую ссылку в структуре можно свободно,
  без владения и подсчёта ссылок.

## Запись 10 — 2026-07-14. Эластичная панель вкладок

### Что сделано

Раньше при большом числе вкладок панель просто вылезала за правый край окна:
каждая вкладка занимала свою «естественную» ширину, и ничего с этим не делалось.
Теперь панель ведёт себя как в браузере — пока места хватает, вкладки обычные,
а когда перестаёт хватать, они ужимаются, и длинные заголовки обрезаются
многоточием. Изменения — только в `ui/main.slint`, Rust-код не тронут.

### Новое в Slint: как layout делит ширину

**1. Кто виноват: `alignment: start`.** С этим свойством `HorizontalLayout`
раскладывает детей по их предпочтительной ширине и прижимает к левому краю —
никакого сжатия, лишнее просто уходит за край. Убрали `alignment` — layout стал
сам распределять доступную ширину между детьми, учитывая их ограничения.

**2. Три размера у каждого элемента.** Layout в Slint оперирует минимальной,
предпочтительной и максимальной шириной ребёнка. Вкладке задали
`max-width: 180px` (потолок даже для длинных имён) и `horizontal-stretch: 0`
(«не расти сверх предпочтительного»). Когда суммарная предпочтительная ширина
больше окна, layout ужимает детей к их минимумам. Аналогия из Java:
`HBox.setHgrow(node, Priority.NEVER)` плюс `setMaxWidth` в JavaFX.

**3. `overflow: elide` у `Text`.** Ключ ко всей задаче: без него минимальная
ширина текста равна полной ширине строки, и ужимать вкладку некуда. С `elide`
текст согласен на любую ширину, а лишнее заменяет на «…» — как
`setTextOverrun(OverrunStyle.ELLIPSIS)` у Label в JavaFX.

**4. Заполнитель-распорка.** Последним ребёнком в layout добавлен пустой
`Rectangle {}` — у него `horizontal-stretch` по умолчанию 1, поэтому всё
свободное место достаётся ему, и вкладки не растягиваются на всю ширину окна,
пока их мало. Точный аналог `Box.createHorizontalGlue()` из Swing.

**5. Крестик закрытия — `Path` вместо символа шрифта.** Раньше крестик был
текстом «✕» (U+2715); такого глифа может не оказаться в системном шрифте
(на Windows вместо него рисуется квадратик), и в разных шрифтах он выглядит
по-разному. Теперь крестик нарисован элементом `Path` — командами в SVG-синтаксисе
(`"M 0 0 L 8 8 M 8 0 L 0 8"` — две перекрещённые линии), со `stroke` вместо
цвета текста. Вектор не зависит от шрифтов и остаётся чётким на любом DPI.
Плюс подсветка под курсором: полупрозрачный фон (`#d0303028` — восьмая пара
hex-цифр задаёт прозрачность), как у вкладок в браузере. Аналогия из Java —
рисование в `paintComponent` через `Graphics2D.drawLine` вместо `JLabel("✕")`.

### Как проверить

`cargo run` → Ctrl+N раз десять: вкладки ужимаются, но остаются в пределах
окна, у активной виден заголовок с «…» и кнопка закрытия. Открыть файл
с длинным именем — вкладка не шире 180px. Закрыть лишние — оставшиеся
возвращаются к обычной ширине.

### Новое в Rust: платформенный код сборки

В Java такого понятия нет: jar иконки не имеет, её задаёт упаковщик
вроде jpackage/launch4j. `winresource` — это «launch4j для Rust»:
компилирует `.rc`-ресурсы и передаёт их компоновщику.

**2. Зависимость только для одной платформы** — секция с `cfg`-условием
в `Cargo.toml`:

```toml
[target.'cfg(windows)'.build-dependencies]
winresource = "0.1"
```

На Linux и macOS в CI крейт даже не скачивается — ресурсов .exe там нет.
Аналогия из Java: Maven-профиль с `<activation><os>`.

**3. `#[cfg(windows)]` на выражении в `build.rs`** — условная компиляция:
на других платформах этого кода просто нет в программе (не «if в рантайме»,
а вырезание на этапе компиляции). Пара к пункту 2: убрали зависимость —
надо убрать и использующий её код, иначе сборка на Linux упадёт.

### Как проверить

`cargo build --release` → в проводнике у `target\release\notepadm.exe`
иконка блокнота (та же, что была у Java-версии). Иконка окна и панели
задач при запуске — как раньше, из `main.slint`.
